## Two targets

Every score in this document answers one of two questions, and between re-pins
they stop giving the same answer.

**Against the pin** is what the oracles measure. `376f6a3` is the commit every
committed corpus was captured from, so a replay is only an oracle for that
revision. This is the number that moves when work lands here.

**Against upstream `HEAD`** is what a user comparing the two products
experiences. On the day of this re-pin the two coincide. The previous pin,
v2.25.7, had fallen two releases behind; the first section below records what
those releases moved, so the drop from 97.2 to 91.6 can be read rather than
trusted, and the second records the ten releases before it, which took the
v2.24.0 pin from 87.8 to 63.7.

Keeping both numbers is deliberate. A port that reaches 100 against a pin it
never advances has not reached parity with anything a user runs. Re-pinning is
the only way to close the second column, and `AGENTS.md` requires regenerating
every committed corpus in the same change, which this pass did.

## Method

Scores measure **reproduced surface**, not behavioral conformance. They come from
diffing inventories, not from running both implementations side by side:

- app-server JSON-RPC method names (146 upstream `SERVER_METHODS` plus 7 `clientTool/*`, counted from the pinned checkout by `scripts/parity/app_server_surface.py`);
- user-facing configuration keys (`vibe/core/config/vibe_schema.py` against
  `LayeredConfig::schema()`);
- published agent tool names and schemas;
- slash commands and CLI flags;
- module presence and depth, measured in lines of production code.

A part scores 100 when its externally observable contract is fully reproduced.
Anything measured only by module presence carries more uncertainty than anything
measured by name-level diff, and the table notes which is which.

Module presence is the weakest evidence there is, and the 2026-08-19 audit
showed why: every subsystem in this port was checked for whether anything
outside its own module and outside test code constructs it, and hooks was the
one that nothing does. A row that says a mechanism is reproduced now means it
runs, not that it compiles. Rows carrying **Measured by a differential oracle**
are replayed against a committed corpus; the others are inventory diffs or
structural judgements, and say so in place.

Every row of the parity table names the reference tree it was measured against,
so a reader can open the same files the score came from. Those paths are
relative to the checkout root recorded in the header and are the state of the
reference at the pin. Citing them rather than quoting them is what `NOTICE`
requires.

Where a differential oracle exists, the score comes from running it rather than
from reading source, and the row says so and carries the figure the replay
prints. Fifty-seven modules matching `*_parity_tests.rs` hold those replays,
against corpora captured by the forty-five capture scripts under
`scripts/parity/` and the eight runtime oracles under
`crates/vibe-cli/tests/runtime-parity/`. The capture scripts sit beside four
helpers, `harness.py`, `pin.py`, `scenarios.py` and `voice_behavior.py` (which
`voice.py` drives), that capture nothing themselves. Four of them read the tool surface from a different angle:
`tool_surface.py` for the published names and schemas, `tool_config.py` for
the per-tool configuration keys, `tool_execution.py` for what a call returns
and `tool_presentation.py` for how a call and its result are shown, the last
of which drives the reference's own `ToolUIDataAdapter`. Every one of them
replays unconditionally; only the probe that recaptures from the pinned
checkout skips, so a missing or off-pin reference never fails `cargo test`.
Both counts were recounted 2026-10-08 by listing the files: `ls
scripts/parity/*.py` answers 49, of which the four helpers are not captures,
and `find crates -name '*_parity_tests.rs'` answers 57. A corpus is committed
on the terms `NOTICE` sets: names, pointers, verdicts and counts, with every
reference-authored sentence reduced to a length and a SHA-256. Each replay also
carries a ledger of what is still divergent, and fails both on a divergence no
entry names and on an entry whose divergence has stopped reproducing, which is
what keeps a score from drifting away from the code under it. The v2.25.7
re-pin exercised that second half: where the reference converged on this port, 26
